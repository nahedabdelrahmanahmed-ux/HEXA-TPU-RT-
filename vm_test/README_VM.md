# محاكاة التطبيقين للجنة داخل VM (بدون عتاد)

## للجنة: أمر واحد
```
./vm_test/committee_run.sh --serve
```
* أول تشغيل يثبّت المتطلبات تلقائياً (يحتاج إنترنت).
* يشغّل خادم oneM2M حقيقي (ACME)، ثم يحاكي **التطبيقين**:
  1. الطيران والـ UAV: reflex لتفادي التصادم في الضباب + خط أنابيب سلامة الهيكل (oneM2M ← 5G URLLC ← MEC ← TPU).
  2. المياه الذكية: reflex لانفجار الأنابيب + محرك MEC للمياه (توقع RUL + فيتو الطرق المائي).
* يطبع ملخصاً في الطرفية ويكتب التقرير `vm_test/results/committee_report.html` (رسوم + جداول + اختبار البيانات التالفة).
* مع `--serve` يُعرض على المتصفح: `http://localhost:8000/committee_report.html` (Vagrant يمرّر المنفذ 8000 تلقائياً؛
  في VM عادي استخدم عنوان الـ VM). بدون إنترنت/ACME: `--no-cse` يستخدم CSE مدمجاً. لتشغيل أسرع: `python3 committee_demo.py --quick`.

## ما لا يستطيع الـ VM إثباته (مهم)
* زمن الـ reflex في التقرير (0.04 µs) **نموذج حسابي بعدد الدورات**، وليس قياساً حقيقياً. الـ VM لا يغيّر ذلك.
  الاختبار C4 يقيس الزمن الفعلي في بايثون تحت ضغط CPU، وهو أبطأ بمراتب (ويظهر فيه max يتجاوز 1ms تحت الحمل).
  قياس الـ hard real-time الحقيقي يحتاج المتحكم/FPGA المستهدف.
* لا يثبت دقة محفزات الطيران/المياه ولا ثوابت Joukowsky (وصفها التقرير بأنها للعرض فقط).
* لا يثبت التوافق مع tinyIoT/Mobius ولا مع MEC sandbox حقيقي.

## تدهور الشبكة بشكل حقيقي (اختياري، يحتاج root)
```
sudo tc qdisc add dev lo root netem delay 20ms 5ms loss 5%   # بطء وفقد على loopback
./vm_test/run_vm_tests.sh onem2m
sudo tc qdisc del dev lo root
```

# ملاحظات مهمة عند عرض النتائج على اللجنة

* **زمن الـ reflex (0.04 µs) نموذج بعدد الدورات.** القياس الفعلي في بايثون تحت ضغط CPU وصل أقصاه إلى ~30 ms
  (الحد 1 ms) مع بقاء نسبة 99% دون 1 ms (اختبار C4). إثبات الزمن الحقيقي يحتاج العتاد المستهدف.
* **`gradual_leak` (مياه) لا يطلق الـ reflex**: الكاشف مصمم للتغيرات المفاجئة (طرق مائي). يلتقطه محرك MEC عبر
  توقع الاتجاه (Bat) ويختار `staged_valve_shutdown`؛ وفي `sudden_burst` يختار `controlled_full_shutdown`. هذا سلوك التصميم.
* **شدة التسرب في عرض المياه افتراض مسمّى** (في `committee_demo.py`): أعمق انخفاض ضغط عن خط الأساس 600 kPa،
  مقيّساً بحيث 40% = 1.0. إذا كانت الشدة < 0.1 يختار المحرك نفسه `hold_flow` (بوابة الخمول). ليست من التقرير الفني الأصلي.
* **فيتو `emergency_full_shutdown` ثابت** ولا يتأثر بالشدة (قفزة Joukowsky = 600 kPa > 500)، لذلك يظهر في كل سيناريو مياه.
  البديل الآمن `controlled_full_shutdown` (إغلاق خلال 30 ثانية، قفزة ≈ 33 kPa) مسموح. طول الأنبوب 1000 م افتراض مسمّى.
* **الـ TPU يعمل مع تطبيق الطيران فقط** (خط أنابيب سلامة الهيكل)؛ لا يوجد حمل TPU لتطبيق المياه في المشروع الأصلي.
* محفزات الطيران والمياه للعرض التوضيحي وغير معتمدة ميدانياً. التوافق مُختبر مع ACME فقط (لا tinyIoT/Mobius ولا MEC sandbox حقيقي).
* التقرير الفني المحدَّث: `Technical_Report_rev2.docx`.

# التحديث الثالث: التوأم الرقمي، MEC Sandbox، والبيانات الحقيقية

* **التوأم الرقمي** (`twin/water_moc.py`): محاكي طرق مائي بطريقة الخصائص (MOC). يطابق حلولاً تحليلية (Joukowsky، الدورة 4L/a،
  التقارب) ويطابق محاكياً مستقلاً (TSNet) بفرق 0.2–0.8% في الذروة. أثبت أن **فيتو الكود آمن فيزيائياً**: لا إجراء مسموح يتجاوز 500 kPa،
  وتقدير الكود متحفظ بنحو 30% (ويقلّل فقط الإغلاق الفوري الكامل بـ 1.2%، وهو محظور أصلاً). الحد الأدنى للانفجار الذي يراه الـ reflex ≈ 5 L/s.
* **عميل MEC 011** (`mec/mec_sandbox_client.py`): `confirm_ready` / تسجيل واكتشاف الخدمات / `confirm_termination`، مع منصة محاكاة صارمة للاختبار.
  **لم يُجرَّب على Sandbox الحقيقي** (غير متاح من بيئة التطوير). شغّل من جهازك:
  `python3 vm_test/mec_sandbox_smoke.py https://<sandbox-host>/<sandbox-name> --app-id <id>` وأرفق المخرجات بتقرير المسابقة
  (أو `python3 committee_demo.py --mec-url <url>` ليظهر في تقرير اللجنة). `--mock` للتجربة المحلية.
* **البيانات الحقيقية** (`real_data/`): تدهور حقيقي لتحمّلات (PHM 2012). Bat: صفر إنذارات كاذبة، وإنذار قبل الفشل في الحالات الأربع،
  لكن بمهلة قصيرة (1–5% من العمر) لأن الأعطال الحقيقية مفاجئة. الجرد الكامل للمصادر والثغرات في `real_data/README.md`:
  لم أجد بيانات متاحة للطيران ولا لكمون 5G؛ وبيانات Perugia التجريبية للطرق المائي (Zenodo 6984669) محجوبة من بيئتي — نزّلها وقارنها بالتوأم.
* اختبارات الطفرات: 12 عطلاً مقصوداً حُقن في المحاكي والفيتو والعميل، واكتشفتها الاختبارات كلها (طفرة أولى صغتها بالاتجاه الخاطئ نجت فصحّحتها).
* إجمالي الاختبارات الآن 193. التقرير الفني: `Technical_Report_rev3.docx`.

# إضافة: متصفح Mobius4 TUI لفحص موارد oneM2M (اختياري)

أداة طرفية (terminal) من مشروع Mobius4 تعرض شجرة موارد oneM2M وتفكّ ترميز السمات وتراقب التغيّر حياً. تعمل مع **أي CSE** عبر HTTP، فتعمل مع ACME في مشروعك.
```
./deploy/get_mobius4_browser.sh        # ينزّل الأداة ويتحقق من SHA-256 (المنشور + المثبَّت) إلى tools/
./vm_test/inspect_cse.sh               # يشغّل ACME ويملؤه بنتائج عرض اللجنة ثم يفتح المتصفح
./vm_test/inspect_cse.sh --live        # + مغذٍّ حيّ: اختر reflexEvents واضغط w للمراقبة
```
ماذا سترى: لكل سيناريو AE (`aviation-…` و`water-…`)، وتحت كل AE حاويتان: `sensorData` و`reflexEvents` (instance لكل عينة أطلقت الـ reflex)، والمفتاح `R` يعرض الـ AEs وأنواع تطبيقاتها.
**تنبيهات:** الأداة طرف ثالث وغير مضمّنة في المشروع؛ جُرّبت النسخة 0.15.0 على Linux x86_64 فقط (لم تُجرَّب على Windows/macOS)؛ المراقبة الحيّة polling لأن ACME بلا MQTT؛
لا تستخدم مفاتيح الكتابة (`n` `e` `D`) أثناء تشغيل عرض أو اختبار. التفاصيل في `docs/CSE_INSPECTION.md` وعيّنة شاشات حقيقية في `docs/tui_example.md`.
